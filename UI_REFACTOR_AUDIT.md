# PennyWise Accounting UI refactor audit

## Audit scope and baseline

This audit covers the current browser application before the PennyWise visual migration. The product has no client framework or URL router: `apps/web/index.html` contains the semantic surfaces, `apps/web/app.js` manages workspace state and API-backed interactions, and `apps/web/styles.css` is the shared design system. Workspaces are revealed by `activeWorkspaceId`, subviews use tabs or `data-*` state, and the shell preserves browser state with `clearledger_*` storage keys. Those internal keys, API headers, package names, and controlled-share URLs remain compatibility identifiers during the PennyWise rename.

The primary reference is the supplied PennyWise Visual Atlas and UI Refactor Prompt Pack. They are workflow and visual-system references only; PennyWise must use its own copy, geometry, and iconography.

## Technology, boundaries, and current UI contracts

| Area          | Current implementation                                                                                                             | Refactor constraint                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Browser shell | Static semantic HTML plus ES modules (`apps/web/index.html`, `app.js`)                                                             | Preserve element IDs, `data-workspace-target`, form names, and event bindings until all callers/tests migrate together. |
| Styling       | One token-driven CSS file with theme, density, text-scale, motion, shell, workspaces, and responsive rules (`apps/web/styles.css`) | Extend the existing tokens; do not introduce a second CSS system.                                                       |
| State         | In-memory workspace data, `sessionStorage` and `localStorage` preferences/drafts                                                   | Keep existing keys and restore behavior; visual changes must not discard Brady's or another tester's local state.       |
| API/data      | Fastify, Zod, Prisma-backed API under `apps/api/src`; browser calls use `api()` and tenant headers                                 | UI work must preserve validation, money/date formatting, permissions, idempotency, and accounting controls.             |
| Identity      | OIDC in production-style runtime; localhost development identity; controlled shares inject tenant identity in `serve.mjs`          | Do not loosen controlled-share authentication or edit the QBWooBridge production deployment.                            |
| Accessibility | Semantic sections, dialogs, labels, live regions, and Playwright accessibility/release checks already exist                        | Retain landmark, focus, keyboard, and status-announcement contracts while changing visual density.                      |
| Tests         | Vitest, Node asset/money tests, Playwright browser matrix, integration tests, accessibility/security/release scripts               | Preserve stable selectors and add focused visual/interaction coverage before changing each workflow.                    |

## Current visual debt to resolve

1. The primary interface combines a top navigation, optional secondary rail, workspace tabs, and large section banners; the hierarchy is capable but too layered for high-frequency accounting work.
2. Many workspaces use repeated `h2` sections and framed cards where a compact queue/table/inspector composition would keep more decision context visible.
3. The theme tokens are mature but the default palette, header height, control height, and some padding values are more spacious and blue/teal than the required PennyWise navy/ivory/teal/copper system.
4. Floating-window mode is powerful but must be reframed as a focused work pane rather than a general replacement for the desktop shell.
5. Record-heavy screens need a shared dense-table and inspector treatment with explicit responsive drawer behavior instead of each workflow inventing its own panel density.
6. The existing app has strong behavior and tests but no route-by-route visual-evidence ledger; `UI_VISUAL_COVERAGE.md` is required before declaring the migration complete.

## Recommended implementation order

1. Finalize/verify the PennyWise display rename without changing internal compatibility identifiers.
2. Add the PennyWise tokens, original mark, sizing scales, focus/semantic status rules, and shared CSS primitives; document them in `UI_REFACTOR_GUIDE.md`.
3. Migrate shared shell, top toolbar, navigation, global search/create, dialogs, and responsive rail/drawer behavior.
4. Migrate high-frequency transactional workflows first: Banking/Reconciliation, Sales/Invoices, Purchases/Expenses, Contacts, Ledger/Journals, and Tax/Month close.
5. Migrate operations and analysis: Inventory, Projects/CRM, Reports/Budgets, Fixed assets, Commerce integrations, and Payments/POS.
6. Migrate setup, settings, switching/import, help, about, auth, and offline states.
7. Run the density/responsiveness pass and route-level screenshot/state gate; record real evidence in `UI_VISUAL_COVERAGE.md`.
8. Run the full functional, accessibility, integration, release, and controlled-share browser verification before declaring completion.
