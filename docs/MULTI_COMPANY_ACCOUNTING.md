# Multi-company accounting boundary

ClearLedger now distinguishes the organization/workspace tenant from its legal
companies. Existing organizations receive one default company during migration;
new organizations create the same default company during bootstrap.

## Current behavior

- `Company` stores legal name, display name, status, base currency, locale,
  timezone, fiscal-year settings, setup status, and default-company identity.
- `CompanyMembership` stores a company-specific role for an active workspace
  member. Company membership is always checked after organization membership and
  cannot cross organization boundaries.
- Session and development request context carry `activeCompanyId`. The web shell
  exposes an explicit company selector beside the organization selector.
- Account, fiscal-period, journal, and journal-line records carry company
  provenance. Existing records are backfilled to the default company, and core
  reads/posts use the trusted company context when present.
- Account, period, and journal uniqueness is company-scoped for company-owned
  records. Legacy rows without a company retain workspace-scoped compatibility
  uniqueness until their domain surface is migrated.
- New companies receive a copy of the active company chart of accounts but no
  journals or posted history. Fiscal setup and opening balances remain explicit
  company setup work.
- Company creation, switching, member listing, and company-role assignment are
  auditable. Ownership cannot be removed from the last company owner.
- Intercompany transactions have an explicit `DRAFT → PROPOSED → APPROVED` review
  path. They are evidence records only; `POSTED` requires two linked journals and
  balance evidence and is not generated by this foundation.
- Consolidation groups can be configured with active company members. They report
  `CONFIGURATION_REQUIRED` until elimination mappings are explicitly supplied and
  never create consolidation journals implicitly.

## API surface

- `GET /v1/organizations/current/companies`
- `POST /v1/organizations/current/companies`
- `POST /v1/organizations/current/companies/switch`
- `GET /v1/organizations/current/companies/:companyId/members`
- `PATCH /v1/organizations/current/companies/:companyId/members/:userId`
- `GET|POST /v1/organizations/current/intercompany/transactions`
- `POST /v1/organizations/current/intercompany/transactions/:transactionId/transition`
- `GET|POST /v1/organizations/current/consolidation-groups`

All endpoints require the existing identity, organization membership, permission,
RLS, and recent-auth controls. A browser-provided company identifier is never
accepted without a server-side `CompanyMembership` match.

## Compatibility boundary

The migration is deliberately staged. Domain tables that still only carry
`organizationId` remain organization-scoped and must not be described as fully
company-isolated. Before a domain creates or posts company-owned data, it should
carry `companyId`, pass it through `withTenantTransaction`, and include it in
idempotency, job, import, connector, report, export, and cache keys. Intercompany
and consolidation automation remains explicit configuration work; no unsupported
automatic journals are generated by this foundation.
